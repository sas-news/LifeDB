# Objective

- The original request is to turn the rough LifeDB design supplied in the conversation into a robust, internally consistent, executable personal-memory database, working in the order philosophy -> architecture -> specification -> implementation -> verification.
- The intended product is a local-first LifeDB v0.2 reference kernel whose durable state survives loss of databases, models, agents, containers, and all of `runtime/`.
- The design is based on four stores: owner-accepted Markdown Canon, immutable Evidence captures/events, content-addressed Objects with an independent retention lifecycle, and disposable Runtime projections.
- Canon targets OKF v0.2 and adds path-independent UUIDv7 identity plus typed Claims under `x-lifedb`.
- The intended final outcome for this repository is an honest v0.2 executable specification: durable capture/event formats, explicit Candidate/Canon transactions and rollback, typed evidence requirements, manual retention with recovery, authorized lexical Context Packs, CLI/HTTP access, schemas, packaging, Docker deployment, and a reproducible empty-runtime recovery drill. Features not actually implemented must remain explicitly out of scope.

# Important Decisions

- Canon is the owner's accepted current semantic model, not objective truth. Evidence proves only what LifeDB recorded, not that a source or statement is authentic or correct.
- Durable authority is split from payload availability. Evidence envelopes/events may remain while large or reproducible payload Objects are evicted under policy.
- `runtime/` is never authoritative and must be deletable and reconstructable without a network call or the original AI model. This is why retention recovery was changed to use the durable prepared event rather than a runtime preview.
- Normal Evidence/history changes are append-only. Correction creates a new Claim and supersession edge. Owner-authorized erasure has precedence in the design but its preview/apply API is intentionally not implemented in v0.2.
- Stable IDs are UUIDv7. Paths, filenames, product names, and agent names are never semantic identities.
- Canon remains human-readable UTF-8 Markdown/YAML and is an OKF v0.2 profile. Existing/unknown OKF fields must survive Canon rewrites. LifeDB-specific fields live in `x-lifedb`.
- Claims separate `basis`, `certainty`, lifecycle `state`, observation time, real-world validity, typed object values, and typed Evidence requirements (`raw`, `representation:<role>`, `record-only`). Numeric LLM confidence is not Canon authority.
- Ingestion creates Evidence only. Canon changes go through explicit Candidate creation and manual promotion with before/after snapshot Objects and prepared/committed events. Automatic AI extraction/promotion is deliberately outside v0.2.
- Retention is never scheduled automatically. Preview is a disposable proposal and exact-confirmation input. Once `retention.apply-prepared` is durable, its exact candidate manifest plus durable Evidence/Objects/quarantine is the crash-recovery authority. The confirmation digest records binding to the prior explicit preview but cannot be recomputed from the smaller prepared event alone.
- The reference uses one durable writer and one owner Bearer token. It has no per-operation scopes or multi-writer/multi-device synchronization.
- The hardened SQLite implementation intentionally fails closed without Linux/POSIX `/proc/self/fd`; it must not silently fall back to a pathname-raceable database connection.
- Descriptor/no-follow hardening protects against path substitution and accidents but cannot provide complete isolation from a fully malicious same-UID process or host administrator. OS permissions/encryption remain deployment boundaries; documentation must say this plainly.
- SHA-256 is byte identity/integrity and deduplication, never source authenticity.
- Git is optional review tooling and is not a LifeDB backup. This particular checkout currently has no functional Git metadata.
- Preserve the explicit v0.2 exclusions: MCP, vectors/learned ranking, external collectors, OCR/caption/transcription, universal agent hooks, automatic reconciliation/eviction, owner-erasure execution, multi-device sync, application encryption, and signatures are not implemented.
- Do not delete, reset, stash, revert, or overwrite unknown files. The workspace has no Git baseline, so every existing file must be treated as user-owned/current state.

# Known Problems

1. `Vault.init()` does not create `evidence/_events`. `reset_runtime()` treats `evidence/_events` as required durable layout, so a freshly initialized vault with no event yet can fail the guarded runtime-reset preflight.
2. Fresh `canon/index.md` lacks the recommended OKF v0.2 frontmatter (`okf_version: "0.2"`). Existing index files must still be preserved on re-init.
3. The descriptor-rooted Vault-init rewrite has no newly added tests for root-name replacement during init, child-directory symlink races, concurrent initializers, or the complete exact fresh layout. The Luna assigned to this work stopped on its usage limit.
4. The complete test suite has not been run after the latest Vault, retention, validation, index, and authentication changes. Treat the tree as actively in progress, not release-ready.
5. `docs/verification.md` is obsolete v0.1 material and contradicts the current source/test/Docker environment.
6. Documentation overstates Canon transaction fields. `docs/philosophy.md` and ADR 0002 say each transaction contains reason, producer/model version, and schema/policy versions; current promotion manifests contain transaction/operation/actor/candidate/claim/before/after/path/document (and rollback-specific fields). Either implement the extra fields deliberately or, preferably for the finite v0.2 reference, downgrade them to optional/future/full-deployment recommendations.
7. ADR 0002 says every event contains reason, policy version, and idempotency key. These are only meaningful for applicable event types and are not universal in the event schema/implementation.
8. `SPEC.md` says installed/vault schemas have “no independent cap,” but `MAX_SCHEMA_BYTES` is 4 MiB. The specification should state the implemented 4 MiB per-schema bound.
9. The Linux/POSIX `/proc/self/fd` dependency of safe SQLite search/rebuild is not documented clearly. The code intentionally fails closed elsewhere.
10. The threat model says other local processes are untrusted but does not clearly delimit same-UID/host-admin guarantees. Descriptor hardening is useful, but complete isolation requires OS permissions/separate principals and is not provided by this process.
11. The new retention test uses the word “signed” for an integrity-sealed event. LifeDB currently has hashes, not digital signatures/authenticated records.
12. The new descriptor-rooted source fingerprint does not by itself prove every higher-level index parse is immune to a fully malicious same-UID process that can rename real directories transiently. Canon reading is descriptor-rooted and Evidence/object reads have boundary checks, but the complete rebuild path needs focused adversarial review and tests before making a stronger claim.
13. Retention recovery's optional preview-presence check begins with pathname `os.lstat(plan_path)` before `_load_plan()` performs its safer bounded open. It is read-only and under the writer/layout guard, but its behavior under a transient runtime-parent replacement has not been reviewed after the latest change.
14. No current Git baseline exists. Do not attempt to infer “modified” versus “original” solely from timestamps or generated artifacts.
